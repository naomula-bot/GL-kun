# Terasoluna観点のレビューガイドライン

## 概要
TERASOLUNA Framework（NECが提供するJavaWebアプリケーション開発フレームワーク）
及びTERASOLUNA開発標準ガイドラインに基づくレビュー観点。
Spring Framework、MyBatis等を基盤とするアーキテクチャを前提とする。

## アーキテクチャ・レイヤー設計

### レイヤードアーキテクチャの遵守
- プレゼンテーション層 / アプリケーション層 / ドメイン層 / インフラ層の分離が適切か
- 各レイヤーの責務が正しく定義されているか
- 上位レイヤーから下位レイヤーへの依存のみ許可されているか（逆方向の依存がないか）
- Controller → Service → Repository のフローが設計されているか

### コンポーネント設計
- Controller: 入力値検証・サービス呼び出し・画面遷移制御のみを担当しているか
- Service: ビジネスロジックが集約されているか（トランザクション制御含む）
- Repository: データアクセスロジックのみを担当しているか
- Domain Object（Entity）: ビジネスルールを適切にカプセル化しているか

## データアクセス設計

### MyBatis利用時の観点
- SQLMapperとEntityの対応関係が明確か
- N+1問題が発生する設計になっていないか
- 適切なフェッチ戦略（Lazy/Eager）が設計されているか
- 動的SQL（`<if>`, `<choose>`等）の利用が適切か

### トランザクション設計
- トランザクション境界が適切に定義されているか（@Transactional の配置）
- 排他制御方式（楽観ロック/悲観ロック）が設計されているか
- 複数DB・複数リソースへのアクセス時の整合性が考慮されているか

## 入力値検証・エラーハンドリング

### Bean Validation
- 入力検証はBean Validation（@NotNull, @Size等）を活用しているか
- カスタムバリデーションの実装方針が示されているか
- 相関チェック（複数フィールドの組合せ検証）の設計が明確か

### 例外ハンドリング
- 業務例外（BusinessException）とシステム例外の分類が適切か
- 例外ハンドリングの階層（Controller/Service/Repository）が設計されているか
- エラーメッセージの国際化対応（i18n）が考慮されているか
- @ControllerAdvice による共通ハンドリングが設計されているか

## セキュリティ設計

### Spring Security
- 認証・認可の設計が明確か
- CSRF対策が設計されているか
- XSS対策（出力エスケープ）が設計されているか
- セッション管理（タイムアウト・固定化対策）が設計されているか

### SQLインジェクション対策
- パラメータバインドが適切に設計されているか（直接文字列連結の排除）
- PreparedStatement / MyBatisの`#{}`を使用しているか

## 共通機能設計

### ロギング
- ログ出力レベル（TRACE/DEBUG/INFO/WARN/ERROR）の使い分けが設計されているか
- ログ出力項目（ユーザーID・セッションID・操作内容）が設計されているか
- 機密情報のマスキングが設計されているか

### ファイル操作
- ファイルアップロード・ダウンロードのセキュリティ考慮が設計されているか
- 一時ファイルの管理（作成・削除）が設計されているか

## 試験設計観点（Terasoluna準拠）

### 単体テスト
- JUnit + Mockito を使用したテスト設計か
- Controller層のテストにMockMvcを使用しているか
- Repository層のテストにH2等のインメモリDBを使用しているか
- テストデータの独立性が確保されているか（DBCleanerやTransaction Rollback）

### 結合テスト
- レイヤー間の統合が確認できるテスト設計か
- 外部システム連携のモック化方針が明確か
- テスト環境の設定管理（application-test.yml等）が設計されているか
