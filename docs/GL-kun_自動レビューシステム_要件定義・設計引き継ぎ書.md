# GL-kun 自動ドキュメントレビューシステム — 要件定義・設計引き継ぎ書

> **本書の位置づけ**
> 本書は、社内で別のAIコード生成システム（以下「実装側システム」）に本システムを実装させることを目的とした、**実装着手可能な粒度の要件・設計の引き継ぎドキュメント**です。
> 本リポジトリ（GL-kun）には Python/FastAPI による**参照実装（プロトタイプ）**が存在します。実装側システムは本書の要件を満たせば言語・FW を踏襲する必要はありませんが、参照実装の構成（プロンプト・レビュー観点・API 形）は流用を強く推奨します。
>
> - 想定読者: 実装側AIシステム、および社内開発者・レビュー担当者
> - バージョン: 1.1
> - 作成日: 2026-06-13

## 0. はじめに（人間の読者向けガイド）

> この章は、技術者でなくても本書の全体像をつかめるように、平易な言葉で要点をまとめたものです。
> 1章以降は実装AI向けの詳細仕様です。**まずこの章だけ読めば、何を作ろうとしているかが分かります。**

### 一言でいうと
**「グループリーダー（GL）が手作業でやっている設計書などのレビューを、AIに一次チェックさせる仕組み」** をつくります。本書は、それを社内の別のAIに実装させるための"発注書"です。

### なぜ作るのか（解決したい困りごと）
- レビューがGLの知識と経験に頼っており、**人によって品質がばらつく**。
- GLにレビューが集中し、**レビュー待ちで開発が止まる**。
- 標準ルールや過去版との突き合わせは手間がかかり、**見落としが起きる**。

→ AIに一次レビューを任せ、GLは最終確認に集中できるようにします。

### どう動くのか（使う人の体験）
1. 担当者が、作った文書（Word・Excel・PowerPoint）を**社内サーバーの決められたフォルダに置く**。
2. 画面で「どの案件の・どの文書を・どの種類として」レビューするか選んで実行する。
3. AIが、**会社の標準ルール・今回のプロジェクトのルール・（改修なら）前のバージョンの文書**と照らし合わせる。
4. 数十秒で**「総合評価（A〜D）＋指摘事項＋改善提案」**が画面に表示される。
5. 結果はフォルダに保存され、後から見返せる。

### AIが何と照らし合わせるか（レビューの"ものさし"）
| ものさし | 中身 | たとえると |
|---|---|---|
| マクロ標準 | PMBOK など会社・業界共通の決まり | 「世の中の常識・業界ルール」 |
| プロジェクト標準 | 今回の案件固有のルール（命名規約など） | 「今回の現場のローカルルール」 |
| 旧版（前のバージョン） | 改修前の要件定義・設計・試験項目 | 「前回の答案。今回どこを直したか・直し忘れがないか」 |
| 文書フォーマット基準 | 各文書に必ず書くべき項目 | 「記入漏れチェックシート」 |

### 対応する文書（全6種類）
提案書／要件定義書／基本設計書／詳細設計書／試験項目書／試験結果報告書。
（※今ある試作品は後ろの3種に対応済み。残り3種の追加を実装AIに依頼する内容です）

### バージョンアップ・機能追加のときの特長
ただ新しい文書を見るだけでなく、**前のバージョンと突き合わせて**「変更は妥当か」「直し忘れ（影響漏れ）はないか」「要件→設計→試験の対応がとれているか」までチェックします。これが本システムの目玉機能です。

### 注意してほしいこと（人として押さえる点）
- **AIは一次レビューであり、最終判断はGL（人）が行います。** AIの指摘には誤りや見落としもあり得ます。
- **文書の中身はAIサービス（社外）に送られます。** 機密文書を扱うため、会社のAI利用ルールに沿って「送ってよい文書か」を事前に決めておく必要があります（詳細は13章）。
- ExcelやPowerPointのレイアウトが複雑だと、文字の読み取りが完全でない場合があります。

### この試作品（GL-kun）との関係
本リポジトリには、考え方を確かめるための**動く試作品**が入っています。実装AIはこれをまねて作れば早い、という"お手本"です。本書はその試作品を、会社で本格利用するために**機能を足して仕様化**したものです。

## 1. 背景・目的

### 1.1 背景
システム開発（新規・バージョンアップ・機能追加）では、担当者が作成する各種ドキュメント（提案書・要件定義書・設計書・試験項目書 等）を、グループリーダー（GL）が以下の基準に照らしてレビューしている。

1. **マクロ的な開発標準** … PMBOK 等の全社・業界横断の開発規定文書類
2. **今回利用する開発標準** … プロジェクトごとに定める開発の進め方ルール（命名規約・設計ルール・採用フレームワーク標準 等）
3. **過去資産** … バージョンアップ・機能追加の場合の旧版（要件定義書・設計書・試験項目書）
4. **ドキュメント品質基準** … 必須記載項目・整合性・トレーサビリティ 等

このレビューは GL の知識と工数に依存し、属人化・レビュー品質のばらつき・レビュー待ちのボトルトネックが発生している。

### 1.2 目的
担当者が **ローカルサーバーの所定フォルダに置いたドキュメント** を、上記の各標準・過去資産に照らして **AI（Claude）が自動レビューし、フィードバックを返す** 仕組みを構築する。GL のレビューを代替するのではなく、**一次レビューの自動化により GL の負荷を下げ、レビュー品質を均質化する**ことを狙う。

### 1.3 達成イメージ（スコープの中心）
- 担当者がドキュメント（Word / Excel / PowerPoint）を所定フォルダに置く
- システムがそれを読み取り、標準類・過去資産と突合してレビューする
- 指摘・改善提案・総合評価をフィードバックとして提示する
- バージョンアップ／機能追加時は**旧版との差分・影響漏れ**まで確認する

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| マクロ標準 | PMBOK 等、全社・業界横断で適用される開発規定文書類 |
| プロジェクト標準 | 当該プロジェクトで定める開発ルール（命名・設計・採用FW標準など） |
| 旧版（baseline） | バージョンアップ・機能追加時の改訂前の要件定義書・設計書・試験項目書 |
| レビュー対象文書 | 担当者が今回レビューを依頼する文書 |
| 案件 | レビューの単位となるフォルダ。1 案件 = 1 つの開発タスク（VUP/機能追加/新規） |
| トレーサビリティ | 要件 → 設計 → 試験項目 の対応関係が追跡可能であること |

## 3. 対象ドキュメント種別

実装側システムは、最低限**以下の文書種別**に対応すること。各種別は固有のレビュー観点（→ 8章）を持つ。

| ID | 文書種別 | レビューの主眼 |
|---|---|---|
| `proposal` | 提案書 | 目的・体制・スコープ・前提/制約・概算規模の妥当性 |
| `requirements` | 要件定義書 | 機能/非機能要件の網羅性・一意性・テスト可能性、提案書との整合 |
| `basic_design` | 基本設計書 | 要件定義書との整合、機能/データ/IF設計、非機能対応 |
| `detail_design` | 詳細設計書 | 基本設計との整合、実装可能な粒度、プロジェクト標準/FW標準準拠 |
| `test_spec` | 試験項目書 | 要件・機能への網羅性、手順の具体性、判定基準の明確さ |
| `test_result` | 試験結果報告書 | 数値整合、品質評価、リリース判定の妥当性 |

> 参照実装は `basic_design / test_spec / test_result` の3種に対応済み。実装側は `proposal / requirements / detail_design` を追加すること。

## 4. 機能要件

### FR-1 ローカルフォルダからのドキュメント取り込み
- **FR-1.1** ローカルサーバー上の所定ルート（例 `data/inbox/`）配下の**案件フォルダ**を一覧取得できること。
- **FR-1.2** 案件フォルダ内のレビュー対象ファイルを一覧取得し、ユーザーが選択できること。
- **FR-1.3** 以下のファイル形式からテキストを抽出できること（**必須**）。
  - **Word（.docx）** … 本文・見出し・表（テーブル）を抽出
  - **Excel（.xlsx）** … シート単位でセルを抽出（行列構造を保ったテキスト化。試験項目書・課題管理表で多用）
  - **PowerPoint（.pptx）** … スライドごとのテキスト・表・ノートを抽出
  - 補助的に `.md / .txt` も受け付けてよい（任意）
- **FR-1.4** 抽出に失敗したファイル（パスワード保護・破損・旧形式 `.doc/.xls/.ppt` 等）は、エラー理由を明示してスキップし、処理全体を止めないこと。
- **FR-1.5** 画像化された表・スキャンPDF等、テキスト抽出できない箇所は「抽出不可」として明示する（OCR は本フェーズの必須要件外）。

#### 案件フォルダ構成（規約）
実装側は以下のフォルダ規約を採用すること。各サブフォルダは存在しなければ無視する（任意）。

```
data/inbox/<案件名>/
├── _baseline/      # 旧版資産（VUP/機能追加時）: 旧 要件定義/設計/試験項目
├── _standards/     # 今回のプロジェクト標準（命名規約・設計ルール等の文書）
├── _reference/     # 提案書・課題管理表など参考資料（任意）
└── <対象文書ファイル>   # 今回レビューする Word/Excel/PowerPoint
```

- マクロ標準（PMBOK 等）は案件横断で共通のため、**システム側の知識ベース**（→ FR-2）として保持し、案件フォルダには置かないことを基本とする。
- プロジェクト標準は案件ごとに異なり得るため、`_standards/` または後述のプロジェクトコンテキストで与える。

### FR-2 知識ベース（標準類）の管理
- **FR-2.1 マクロ標準**: PMBOK 等のレビューガイドラインをシステムに常駐保持する。参照実装の `backend/prompts/pmbok.md` を初期セットとして流用すること。
- **FR-2.2 開発標準/フレームワーク標準**: 採用 FW の標準（参照実装は Terasoluna）を保持。プロジェクトに応じて差し替え・追加可能であること。
- **FR-2.3 ドキュメントフォーマット基準**: 文書種別ごとの必須記載項目・品質チェック観点（参照実装の `doc_formats.md`）を保持。`proposal/requirements/detail_design` 分を追記すること。
- **FR-2.4** これらの知識ベースは **Markdown ファイル等で外出しし、コード変更なしに編集・追加できる**こと（メンテ性要件）。

### FR-3 プロジェクトコンテキストの登録
参照実装の `data/context.json` 相当を保持し、以下を事前登録・編集できること。
- プロジェクト概要（システム名・技術スタック・体制）
- プロジェクト固有ルール・規約
- 最近の課題・障害・インシデント（過去の教訓を重点確認に反映）
- 追加チェックリスト（プロジェクト固有の確認事項）

### FR-4 レビュー実行
- **FR-4.1** ユーザーは「文書種別」「レビュー対象（取り込みファイル or 貼り付けテキスト）」を指定してレビューを実行できる。
- **FR-4.2** システムは「マクロ標準＋プロジェクト標準＋ドキュメント基準＋プロジェクトコンテキスト＋（該当時）旧版」を文脈として AI に渡し、レビュー結果を生成する。
- **FR-4.3** レビュー結果は**ストリーミング**でリアルタイム表示する（参照実装踏襲）。
- **FR-4.4** レビュー結果は以下の定型フォーマットで出力する。
  1. **総合評価**（A:問題なし / B:軽微な指摘 / C:要修正 / D:重大な問題）
  2. **観点別レビュー**（標準ごとに指摘・改善提案を箇条書き）
  3. **重要指摘事項**（C/D 相当の必須対応を優先順）
  4. **改善提案**
  5. **総評**（GL として次にとるべきアクション）
- **FR-4.5** 結果のコピー／保存（案件フォルダへレビュー結果を書き出す）ができること。

### FR-5 旧版との突合レビュー（バージョンアップ・機能追加）
`_baseline/` が存在する場合、通常観点に加えて以下を実施する。
- **FR-5.1 差分の妥当性**: 旧版から今回版への要件・設計の追加／変更／削除が、提案書・要件定義書の意図と整合しているか。
- **FR-5.2 影響漏れ検出**: 今回の変更が、旧版の関連機能・既存設計・既存試験項目に与える影響が漏れなく反映されているか（回帰観点）。
- **FR-5.3 トレーサビリティ**: 変更要件 → 設計変更 → 試験項目追加/改修 の対応が追跡できるか。
- **FR-5.4** 旧版に存在したが今回版で**消えた記述**が、意図的な削除か抜け漏れかを指摘対象とする。

### FR-6 フィードバックの提示・記録
- レビュー結果を画面表示し、案件フォルダ（例 `data/inbox/<案件>/_reviews/<文書名>_<日時>.md`）に保存できること。
- 同一文書を再レビューした履歴を残せること（任意だが推奨）。

## 5. 非機能要件

| ID | 分類 | 要件 |
|---|---|---|
| NFR-1 | セキュリティ | 社内文書を扱うため、**ローカルサーバー内で完結**する構成を基本とする。外部送信は AI API 呼び出しに限定し、送信先・送信内容（業務文書本文が AI ベンダーへ送られる点）を運用者が把握・承認できること。社内のデータ取扱規程・AI 利用ガイドラインに準拠すること。 |
| NFR-2 | セキュリティ | API キー等の機密情報は環境変数・シークレット管理で扱い、リポジトリにコミットしない（参照実装は `.env` ＋ `.gitignore`）。 |
| NFR-3 | セキュリティ | レビュー対象文書・抽出テキスト・レビュー結果はローカル保存し、`.gitignore` で誤コミットを防止する。 |
| NFR-4 | 性能/コスト | マクロ標準等の静的・大容量プロンプトは**プロンプトキャッシュ**を用いて繰り返し実行時のコスト・レイテンシを削減する（参照実装踏襲）。 |
| NFR-5 | 入力サイズ | 大規模文書（Excel 大量シート等）はトークン上限を超え得る。文書の分割・要約・対象シート選択などのフォールバックを設計すること。 |
| NFR-6 | 可用性/堅牢性 | 1 ファイルの抽出失敗・API エラーで全体が落ちないこと。エラーは利用者に分かる形で表示する。 |
| NFR-7 | 保守性 | レビュー観点・標準類は Markdown 等で外出しし、非エンジニアでも編集できること。 |
| NFR-8 | 監査性 | 「いつ・どの文書を・どの標準で・どう評価したか」を記録として残せること。 |
| NFR-9 | 国際化 | UI・出力は日本語を基本とする。 |

## 6. システムアーキテクチャ

### 6.1 参照実装の構成（流用推奨）
```
GL-kun/
├── backend/
│   ├── main.py          # FastAPI エンドポイント（コンテキスト管理・レビュー）
│   ├── reviewer.py      # Claude API レビューエンジン（プロンプトキャッシュ・ストリーミング）
│   ├── prompts/
│   │   ├── pmbok.md         # マクロ標準（PMBOK）レビューガイドライン
│   │   ├── terasoluna.md    # 開発/FW 標準レビューガイドライン
│   │   └── doc_formats.md   # 文書種別ごとのフォーマット・品質基準
│   └── requirements.txt
├── frontend/            # SPA（HTML/CSS/Vanilla JS、依存ライブラリなし）
└── data/                # コンテキスト・取り込み文書（gitignore）
```

### 6.2 本要件で追加すべきコンポーネント
1. **ファイル取り込み層（新規）**: ローカルフォルダ走査 ＋ Word/Excel/PowerPoint からのテキスト抽出。
   - Python なら `python-docx`（.docx）、`openpyxl`（.xlsx）、`python-pptx`（.pptx）を推奨。
2. **案件・baseline 管理（新規）**: 案件フォルダ規約（4章）に基づく一覧・選択・旧版読み込み。
3. **文書種別の拡張（追記）**: `proposal / requirements / detail_design` の観点とフォーマット基準。
4. **差分レビュー（新規）**: `_baseline/` を文脈に含めた突合レビュー（FR-5）。
5. **レビュー結果の保存（新規）**: 案件フォルダへの結果書き出し・履歴。

### 6.3 データフロー
```
[担当者] → 案件フォルダへ Word/Excel/PPT を配置
                 │
[UI] 案件選択 → 対象ファイル選択 → 文書種別選択 → レビュー実行
                 │
[取り込み層] フォルダ走査 → 各ファイルからテキスト抽出（失敗はスキップ＆通知）
                 │
[文脈構築] マクロ標準 + 開発/FW標準 + 文書フォーマット基準
           + プロジェクトコンテキスト + (該当時) _baseline 旧版
                 │
[AI(Claude)] システムプロンプト(標準類=キャッシュ) + ユーザーメッセージ(対象文書+旧版)
                 │
[出力] ストリーミングでレビュー結果（総合評価/観点別/重要指摘/改善提案/総評）
                 │
[記録] 画面表示 ＋ 案件フォルダへ結果保存
```

## 7. インターフェース仕様（API 案）

参照実装の `POST /api/review`・`GET/POST /api/context` を踏襲し、以下を追加する。RESTでなくとも同等の操作が提供されればよい。

| メソッド | パス | 概要 |
|---|---|---|
| `GET` | `/api/cases` | 案件フォルダ一覧を返す |
| `GET` | `/api/cases/{case}/files` | 案件内のレビュー対象ファイル・`_baseline`・`_standards` の一覧を返す |
| `POST` | `/api/extract` | 指定ファイルからテキスト抽出し、抽出結果・抽出可否を返す |
| `POST` | `/api/review` | レビュー実行（ストリーミング）。入力: 文書種別／対象（ファイル参照 or テキスト）／旧版利用フラグ／コンテキスト上書き |
| `GET` `POST` | `/api/context` | プロジェクトコンテキストの取得・保存 |
| `POST` | `/api/reviews/save` | レビュー結果を案件フォルダへ保存 |
| `GET` | `/api/health` | ヘルスチェック |

### `POST /api/review` リクエスト例
```json
{
  "doc_type": "requirements",
  "source": {
    "case": "2026Q2_受発注VUP",
    "files": ["要件定義書_v2.docx"]
  },
  "use_baseline": true,
  "context_override": null
}
```

> `source` は「ファイル参照（案件＋ファイル名）」または「貼り付けテキスト（`{"text": "..."}`）」のいずれかを受け付ける。

## 8. レビュー観点定義

### 8.1 共通（全文書種別）
- マクロ標準（PMBOK）準拠 … 参照実装 `pmbok.md` 参照（スコープ/スケジュール/品質/リスク/コミュニケーション 等）
- 開発/FW 標準準拠 … 参照実装 `terasoluna.md` 参照（採用 FW に応じて差し替え）
- ドキュメントフォーマット・品質基準 … 必須記載項目／用語統一／曖昧表現（「適宜」「必要に応じて」等）の排除／図表の正確性
- プロジェクト固有ルール・最近の課題への対応

### 8.2 文書種別ごとの主眼（実装側が `doc_formats.md` に追記すべき項目）

**提案書（proposal）**
- 目的・背景・解決したい課題が明確か / 提案スコープと前提・制約 / 体制・役割 / 概算規模・スケジュールの妥当性 / リスクと前提条件の明示。

**要件定義書（requirements）**
- 機能要件の網羅性と一意性（要件 ID 採番）/ 非機能要件（性能・可用性・セキュリティ・運用）の定量定義 / 各要件のテスト可能性 / 提案書との整合 / スコープ内外の明示 / 用語定義の一貫性。

**基本設計書 / 詳細設計書（basic_design / detail_design）**
- 上位文書（要件定義／基本設計）との整合 / 機能・データ・IF 設計の網羅 / 非機能要件の設計反映 / 実装可能な粒度 / プロジェクト標準・FW 標準準拠 / 曖昧表現の排除。
- 参照実装 `doc_formats.md` の「基本設計書」必須記載項目・品質チェック観点を流用。

**試験項目書（test_spec）**
- 要件・機能への網羅性（トレーサビリティ）/ 正常系・異常系・境界値 / 手順の再現性 / 判定基準の定量・客観性 / 項目 ID 採番規則。

**試験結果報告書（test_result）**
- 数値整合（項目数の合計）/ 不具合の重要度評価 / 未実施項目のリスク評価 / リリース判定根拠の明確さ / 残存リスクの識別。

### 8.3 差分レビュー観点（FR-5、`_baseline` 利用時）
- 追加／変更／削除要件の妥当性、旧版設計・試験項目への影響漏れ、変更要件→設計→試験のトレーサビリティ、意図せぬ記述欠落の検出。

## 12. 受け入れ条件（実装側システムへの検収基準）

- [ ] 6種別すべての文書をレビューでき、結果が定型5項目（総合評価/観点別/重要指摘/改善提案/総評）で出力される。
- [ ] ローカル所定フォルダの Word(.docx)・Excel(.xlsx)・PowerPoint(.pptx) を取り込んでレビューできる。
- [ ] 抽出失敗ファイルがあっても処理が止まらず、失敗理由が利用者に表示される。
- [ ] `_baseline/` がある案件で、差分・影響漏れ・トレーサビリティを含む突合レビューが行われる。
- [ ] マクロ標準・FW標準・フォーマット基準・プロジェクトコンテキストがレビュー結果に反映されている（観点別レビューに各標準が現れる）。
- [ ] 標準類・レビュー観点が Markdown 等で外出しされ、コード変更なしに編集できる。
- [ ] 社内文書がローカル完結で扱われ、外部送信は AI API 呼び出しに限定されている（NFR-1〜3）。
- [ ] レビュー結果が案件フォルダに保存され、実施履歴が残る。

## 13. 制約・前提・留意事項

- **AI へのデータ送信**: レビューには対象文書本文を AI API（外部ベンダー）へ送信する。社内の機密区分・AI 利用ポリシーに照らし、対象文書の送信可否を事前に確認・運用ルール化すること。完全オンプレが必須の場合はローカル LLM の採用検討が別途必要（本書のスコープ外）。
- **AI の限界**: 自動レビューは**一次レビュー**であり、最終判断は GL が行う。AI の指摘には誤検出・見落としが含まれ得る前提で運用する。
- **抽出精度**: レイアウトが複雑な Excel/PowerPoint や画像化された表は抽出が不完全になり得る。抽出結果を利用者が確認できる導線を設けること。
- **トークン上限**: 旧版＋対象文書＋標準類を同時に渡すと大きくなる。分割・要約・対象シート選択等のフォールバックを設計すること。
